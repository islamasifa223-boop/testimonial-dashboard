# Agentic Development Workflow

This document records the agentic tooling and review work performed on Kudosly, the
evidence for it, and what remains outstanding. It is written so that a reader can
verify every claim against the repository.

Where this document states a fact, the fact was checked against source. Where it
makes a recommendation, it is labelled as such and no code has been changed on the
strength of it.

---

## 1. Project context and purpose

Kudosly is a testimonial collection SaaS built on Laravel 13 (PHP `^8.4`). Account
owners create branded collection pages called **Spaces**, share a public link, receive
submissions from customers who need no account, and publish approved testimonials as
a **Wall of Love** or an embeddable **widget**.

The full product description is in `PRD.md`; the implementation guide is `CLAUDE.md`;
the schema is documented in `docs/DATA_MODEL.md`.

**Why the tooling work below was done.** The repository already contained a working
application with a full test suite, but two things an agentic submission is normally
expected to demonstrate were absent from it:

- There was no evidence of **two distinct agentic tools** having been genuinely used.
- There was no evidence of **parallel work**.

This document and the work it describes address the first of those. The second is
still outstanding, and section 8 says so plainly.

## 2. The `kudosly-conventions` Skill

### Why it was created

The codebase encodes a number of conventions that are correct but **not discoverable
from the code alone**. A reader cannot infer, for example, that a cross-account
resource must return 404 rather than 403, or that `spaces.slug` is server-generated
while `spaces.name_key` is generated by a model hook — two different mechanisms that
look similar from the outside. `CLAUDE.md` documents these rules for a human or agent
reading it, but there was no mechanism that would automatically load them into a
review.

The Skill packages those rules so they can be applied as a repeatable review, and so
that the review reports findings in a consistent format.

**It was created only after every rule it contains was verified against the source.**
An earlier draft contained four inaccuracies that were corrected before the file was
written; those corrections are recorded in section 2.5.

### Location

```
.puku-cli/skills/kudosly-conventions/SKILL.md
```

This is the project-level skill directory used by the Puku CLI runtime. The runtime
does **not** discover `.claude/skills/` or `.agents/skills/` — those belong to Claude
Code, not to Puku CLI, and the CLI explicitly forbids writing skills there. The two
paths Puku CLI recognises are:

| Scope | Path |
|---|---|
| Project | `.puku-cli/skills/<skill-name>/SKILL.md` |
| User/global | `~/.puku-cli/skills/<skill-name>/SKILL.md` |

The global path was **not** used, so no global settings were changed.

### What it covers

Eleven convention sections, each with the concrete evidence needed to check it:

| # | Convention | Substance |
|---|---|---|
| 1 | Authorization returns 404, never 403 | A 403 confirms an id belongs to a real record. Checks `abort_unless(..., 404)`, `failedAuthorization()` → `abort(404)`, and public-route `abort(404)`. |
| 2 | `#[Fillable]` / `#[Hidden]` attributes | Laravel 13 attribute style, not `$fillable` properties. All five models use it; `#[Hidden]` on `User` only. |
| 3 | Ownership through the space | `Testimonial` and `Widget` carry only `space_id`. Ownership uses `scopeOwnedBy()` → `whereHas('space', ...)`, so soft-deleted spaces are excluded. |
| 4 | Server-generated values | Two distinct mechanisms, kept separate: **model hooks** (`spaces.name_key`, `widgets.public_id`, `users.plan_id`) and **service/controller layer** (`spaces.slug`, `testimonials.photo_path`), the latter of which *are* mass-assignable at the model level. |
| 5 | Moderation flags are server-side only | `approved`, `hidden`, `favorite`, `hearted`, `consented` are not fillable and never come from a form. |
| 6 | Validation lives in form requests | Including the anti-spam token, the honeypot, the uniform failure message, and the fact that `rating` is governed by `spaces.rating_enabled` and is **not** part of the `SpaceField` enum. |
| 7 | Entitlement enforced in one place | `PlanEntitlement` owns enforcement. `User::spacesLimit()` / `testimonialsLimit()` are read helpers it delegates to, not a duplicate path. |
| 8 | Plans granted only by a verified webhook | Fail-closed routing, and the distinction between the **price identity** check (`hash_equals`) and the **status-to-plan** mapping. |
| 9 | Seeding and schema details | `PlanSeeder` idempotency, the never-overwritten `stripe_price_id`, no `customers` table, the two unconstrained Cashier foreign keys, and that the repo's own Cashier migrations are the ones that run. |
| 10 | Test conventions | `RefreshDatabase` on `Feature` only; `seedPlans()` is mandatory; shared helpers live in `tests/Pest.php`. |
| 11 | Frontend conventions | The five Vite entry points, `public/embed.js` staying dependency-free, and Pint with the Laravel preset (no `pint.json`). |

### Verification evidence

**Q1 — Is paid-plan assignment restricted to verified webhook events? Yes.**

A repository-wide search for `plan_id` (excluding `vendor/`, `node_modules/`,
`storage/`, `bootstrap/cache/`) found exactly **one** production writer of the column:

| Location | What it does | Can grant Pro? |
|---|---|---|
| `app/Services/PlanProvisioner.php:127` | `$user->forceFill(['plan_id' => $plan->id])->save();` | **Yes** — the sole writer |
| `app/Models/User.php:64-65` | `creating` hook — assigns **Free** when `plan_id` is null | No |
| `app/Services/PlanEntitlement.php:119` | `$space->user()->value('plan_id')` | No — read only |
| `app/Services/PlanProvisioner.php:123` | comparison of the current plan id | No — comparison only |
| `database/migrations/2026_11_18_000002_add_plan_id_to_users_table.php:15,25` | column definition / rollback | No — schema only |
| `tests/Feature/**` (24 hits) | test setup | No — test scope |

Additional checks that closed the remaining routes:

- `plan_id` is **not** in `User`'s `#[Fillable(['name', 'email', 'password'])`
  (`app/Models/User.php:17`), so no `fill()` or `create()` can set it. Only
  `forceFill()` can, and the sole `forceFill(['plan_id' => ...])` is at
  `PlanProvisioner.php:127`.
- `app/Console/` **does not exist** — no console commands.
- `app/Jobs/` **does not exist** — no queued jobs.
- `app/Listeners/` contains exactly one file, `HandleStripeSubscriptionEvent.php`.
- `app/Livewire/` (`Navigation.php`, `WidgetBuilder.php`) contains no `plan_id`
  reference.
- Raw-SQL write search (`DB::table`, `->update([`, `->increment`, `raw(`) across
  `app/`, `database/`, `routes/` found only `spaces` writes in
  `2026_11_18_000004_add_field_configuration_to_spaces_table.php:66,69,71,107`.
- `Plan::users()` is used **nowhere** — the relation is never used to assign plans.
- `BillingController` only **reads** the Pro plan (lines 32, 51, 110). Its
  `upgrade()` method (lines 47-73) starts a Checkout session and redirects; the
  docblock at lines 44-45 states the invariant, and the code confirms it: the method
  never touches `plan_id`, and the `upgraded` query parameter is consumed only as the
  display-only `$this->upgradePending` (line 36).

**Q2 — Can an unknown Price ID or unknown status incorrectly grant Pro? No, on both.**

*Unknown or malformed Price ID.* `priceIdFromPayload()`
(`app/Services/PlanProvisioner.php:178-187`) returns `null` for a missing,
non-string or empty Price ID. `userForProSubscription()` (line 100) then returns
`null`, and `handle()` (lines 36-40) returns early — **no plan change**. The
comparison is `hash_equals($configured, $priceId)` against `Plan::stripePriceId()`
(line 205), the stored value on the Pro plan row being the sole authority. No live
Stripe API call is made. A subscription on any other Price never changes the plan.

*Unconfigured Pro plan.* `Plan::stripePriceId()` returns `null` when the column is
empty (`app/Models/Plan.php:72-77`), and `isProPrice()` guards it explicitly
(line 204). A missing configuration therefore **fails closed** — it cannot grant Pro.

*Unknown status.* `targetPlan()` (`app/Services/PlanProvisioner.php:149-171`) maps
exactly six Stripe status constants and returns `null` for everything else, including
`paused` and any status Stripe adds in future. `handle()` (lines 42-47) then returns
without writing. **Unknown statuses never grant or revoke a plan.**

*One deliberate semantic worth flagging.* `past_due` and `unpaid` map to **Pro**, not
Free. The docblock at lines 160-161 explains the intent: *"A renewal that failed keeps
the account on Pro until Stripe cancels the subscription, because that subscription
was paid for before."* This is an intentional product decision, not an oversight — but
it is the one place a non-`active` status grants a paid plan, and it is worth
confirming it matches the intended business rule.

**Q3 — Are repeated webhook events handled safely? Yes for identical repeats.**

`sync()` (`app/Services/PlanProvisioner.php:115-128`) has two guards: it returns if
the target plan row does not exist (lines 119-121), and returns if the user is
already on that plan (lines 123-125). A redelivered event therefore performs **no
UPDATE at all**. Delivering the same event 2, 3 or 100 times converges on the same
state with a single write on the first delivery. The write uses `forceFill()`, which
is required here precisely because `plan_id` is deliberately not fillable.

**Q4 — Does PlanSeeder preserve an existing Stripe Price ID? Yes.**

`PlanSeeder::applyStripePriceId()` (`database/seeders/PlanSeeder.php:38-50`) has
three independent guards:

1. `$plan->name !== PlanName::Pro` — the **Free** plan is never given a Price ID.
2. `$plan->stripePriceId() !== null` — an already-stored Price ID short-circuits the
   method, so it is **never overwritten**, not even when `services.stripe.pro_price_id`
   changes in the environment.
3. `! is_string($configured) || trim($configured) === ''` — an unset or blank
   environment variable leaves the plan untouched rather than writing an empty string.

The seeder is idempotent for plan rows: `Plan::updateOrCreate(['name' => ...], $plan)`
matches on the plan name, so re-running updates rather than inserting duplicates.

*Consequence worth noting.* Because a stored Price ID is authoritative and never
refreshed, pointing the application at a **new** Stripe Price object does not take
effect by re-seeding; the stored value must be cleared manually. Correct for a working
environment, but a manual step.

### Final follow-up verification

down: the exact Stripe event names routed to `PlanProvisioner::handle()` and

- **`app/Listeners/HandleStripeSubscriptionEvent.php` was opened in full.** The
  routing is now confirmed: every `customer.subscription.*` event **except**
  `customer.subscription.deleted` goes to `handle()`, and that one exact event name
  alone goes to `revoke()`. All other event types — `invoice.*`, `checkout.session.*`,
  `charge.*` and the rest — are rejected before either method is reached.
- **A repository-wide search for `plan_id`** outside `vendor/`, `node_modules/`,
  `storage/` and `bootstrap/cache/` confirmed that
  `app/Services/PlanProvisioner.php:127` remains the only production writer of the
  column, and that no console command, queued job, listener, Livewire component,
  route, seeder, factory or raw SQL statement can grant Pro.

The findings from this follow-up pass were:

| Severity | Count |
|---|---|
| blocking | 0 |
| should-fix | 0 |
| observation | 1 |

The single observation is the listener-level fail-closed guard at
`app/Listeners/HandleStripeSubscriptionEvent.php:26-30`, which was verified correct.

## 4. Audit limitations

These are stated plainly so that nothing is implied that is not true.

**The billing findings were not obtained from a Subagent.** The billing review was
assigned to a Subagent, but that delegation was interrupted before the Subagent
executed. The billing findings in section 3 are therefore the **primary agent's**
findings, produced by direct inspection of the source files listed there. They were
not corroborated by a second, independent reviewer. Two checks that the Subagent was
supposed to cover — opening `HandleStripeSubscriptionEvent.php` in full, and searching
outside `app/` for other plan-granting paths — were completed afterwards by the
primary agent in a separate step, and their results are recorded in section 3.

## 5. Remaining risks

Two issues from the billing audit are recorded here as **open risks**. No code has
been changed for either, and neither is a known exploit of the running application.

### Risk 1 — Duplicate `stripe_id` on `users`

**Where:** `database/migrations/2026_11_22_183846_create_customer_columns.php:19`
and `app/Services/PlanProvisioner.php:92`

**The risk.** `users.stripe_id` is `nullable()->index()` — indexed, but **not unique**.
`PlanProvisioner::userForProSubscription()` resolves the owning account with:

```php
$user = User::query()->where('stripe_id', $customer)->first();
```

`->first()` on a non-unique column returns an arbitrary matching row. If two accounts
ever end up sharing a `stripe_id` — a data import, a manual database edit, or a
duplicate Stripe customer attached to two local accounts — a paid subscription grants
Pro to whichever row the database happens to return, and the *other* account receives
nothing. The failure is silent: no error is raised, and the paying customer may see
their plan change on the wrong account or not at all.

**Why it is not blocking.** In normal operation `stripe_id` is written by Cashier from
the authenticated session, so duplicates should not arise. The exposure is a
data-integrity failure mode rather than an attacker-controlled path — no user input
sets `stripe_id`.

**Possible remedies, none applied.** A unique index on `users.stripe_id` would make
the invariant explicit at the schema level, but it needs care: Cashier writes this
column and the column is nullable, and existing rows may already contain duplicates
that would block the index. Alternatively, `userForProSubscription()` could assert
that exactly one account matched before granting, and log an error if more than one
did.

### Risk 2 — Out-of-order Stripe webhook delivery

**Where:** `app/Services/PlanProvisioner.php:61-76` (`revoke()`) and
`app/Services/PlanProvisioner.php:115-128` (`sync()`)

**The risk.** `revoke()` downgrades the user to Free unconditionally, and it is
reached only from the literal event type `customer.subscription.deleted`. Nothing
records when a given subscription's last event was applied. If a `deleted` event is
processed before an `updated` event carrying `active` — Stripe does not guarantee
event ordering — the later event moves the user **back** to Pro for a subscription
Stripe has already cancelled.

A related exposure exists within a single event: the read of `$user->plan_id` and the
write in `sync()` are not atomic, and there is no `lockForUpdate()` or surrounding
transaction. Two concurrent deliveries of conflicting events resolve by
last-writer-wins, regardless of which event is newer.

**Why it is not blocking.** It requires either a specific out-of-order delivery or
concurrent conflicting deliveries. A deleted subscription's `updated` event is not
normally re-sent with `active`, and Stripe normally delivers a subscription's events
in order for a given subscription.

**Possible remedies, none applied.** Compare the event's `created` timestamp against
the last-applied event timestamp for that subscription, and ignore an event older than
the one already applied. Such a record needs somewhere to live — a column on
`subscriptions`, or a dedicated table — which is a schema change and therefore a
decision, not a patch. A simpler mitigation, wrapping the `sync()` read-modify-write
in a transaction with `lockForUpdate()`, would address only the concurrency half.
